# Pest-violation risk model

Predicts which New York City restaurants will be cited for pests (rats, mice, roaches or flies) by the Health
Department in the next 60 days. RatSignal shows the highest-risk restaurants in each customer's zip codes on the
**Forecast** tab, so pest-control companies can reach them before the inspector does.

```
riskmodel/socrata.py    paged, retrying client for NYC Open Data
riskmodel/data.py       downloads inspections, 311 rodent complaints and city rat inspections
riskmodel/features.py   point-in-time features and labels (the leakage-sensitive part)
riskmodel/evaluate.py   precision@k overall and per zip, average precision, calibration
riskmodel/train.py      time-split training, baselines, model selection, saved model + reports/metrics.json
riskmodel/score.py      daily batch scorer -> POST /api/admin/risk
riskmodel/monitor.py    scores served forecasts once their 60-day window closes
tests/                  leakage, label and feature tests
```

## Data

| Source | Dataset | Used as |
|---|---|---|
| DOHMH restaurant inspections | `43nn-pn8j` | ~283k violation rows since 2023 → 90k inspections; features and labels |
| 311 service requests | `erm2-nwe9` | rodent complaints per zip per month |
| Rodent inspections | `p937-wjvj` | city rat inspections failed for rat activity, per zip per month |

NYC only. Chicago records violations as free text under a different inspection regime, so pooling the cities
would mix two label definitions.

## Problem setup

- **Unit:** an active restaurant (inspected in the 18 months before the snapshot) on a snapshot date `t`.
- **Label:** 1 if any inspection in `[t, t + 60 days)` cites code 04K, 04L, 04M or 04N.
- **Snapshots:** the 1st and 16th of each month from Jan 2025, about 22–25k restaurants each.
- **Features (31):** last inspection (days since, score, grade, type, pests found, re-inspection pending), past-year
  history (inspections, pest citations by type, scores, closures), cuisine, borough, and zip context (pest
  citation rate, 311 rodent complaints, failed rat inspections over 3 and 12 months).

### Avoiding leakage
- Features only use inspections dated before `t - 4 days` (records reach the portal a few days late) and zip
  aggregates from calendar months that ended before `t`. `tests/test_features.py` checks that features are
  identical whether or not later data exists.
- Splits are by time with a 60-day gap, so no training label overlaps a later period:
  train Jan–Sep 2025 (17 snapshots), validation Nov 2025–Jan 2026 (6), test Apr–Aug 2026 (9).
- Gradient boosting's built-in early stopping holds out random rows. The same restaurant appears in many
  snapshots, so that holdout leaks and the model overfits. It's off; the number of rounds is tuned on the
  time-based validation period.

## Results (test period, Apr–Aug 2026, never used for training or selection)

Base rate: 4.4% of active restaurants get a pest citation in a 60-day window.

| | Precision@100 citywide | Precision@5 per zip | Average precision | ROC-AUC |
|---|---|---|---|---|
| RatSignal's current heat score (baseline) | 7.7% | 8.4% | 0.058 | 0.56 |
| Hand-written rule: re-inspection pending, pests last time, worst score | 15.6% | 13.5% | 0.085 | 0.62 |
| Logistic regression | 25.8% | 18.1% | 0.153 | 0.82 |
| **Gradient-boosted trees (deployed)** | **30.3%** | **20.5%** | **0.181** | **0.85** |

- The model beats both baselines in every one of the 9 test snapshots (19–42% vs 13–17% for the rule).
- Probabilities are reasonably calibrated: the top decile predicts 20% and observes 19%.
- Most important features (permutation importance): last grade, days since last inspection, mean score over the
  past year, cuisine, last score.

Exact numbers are in `reports/metrics.json` and are regenerated by `train.py`.

## Limitations

- **Inspection bias.** A violation is only recorded if an inspector visits, so the model partly learns *who gets
  inspected soon* (for example, a pending re-inspection). That's useful for the product, since those restaurants
  really will be cited, but it isn't pure "has pests". Among restaurants that *were* inspected in the window, the
  model's average precision is 0.435 vs 0.370 for the heat score: a real but smaller gain.
- **Survivorship.** The city's dataset keeps roughly three years per restaurant and drops closed ones. Older
  snapshots under-count history and miss restaurants that closed, which is why training starts in 2025.
- **Static fields** (cuisine, borough, zip) are taken from each restaurant's latest record.
- **Seasonality** is learned from one year of data (`month` feature); pest citations peak in summer.

## Running it

```bash
cd ml
uv sync
uv run pytest
uv run python -m riskmodel.train            # downloads data, trains, writes models/ and reports/
uv run python -m riskmodel.score --no-upload --out forecast.json
```

In production, `.github/workflows/forecast.yml` runs `score` and `monitor` every morning. It needs the
`RATSIGNAL_ADMIN_SECRET` repository secret (the app's `ADMIN_SECRET`). Retrain when the monitored precision on
served forecasts drops below the rule baseline, or every few months.
